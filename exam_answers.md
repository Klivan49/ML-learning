## Вопрос 1: Как вы представили текстовое содержимое файлов в виде числовых признаков?

**Ответ:** Мы используем два подхода — статистический и векторный.

### Статистический подход (ручные признаки)
Для текстовых файлов (`.txt`, `.py`, `.csv`, `.json` и т.д.) извлекаем простые числовые характеристики:
- `text_length` — длина текста в символах
- `text_word_count` — количество слов
- `text_line_count` — количество строк
- `text_unique_word_ratio` — доля уникальных слов (мера лексического разнообразия)
- `text_avg_word_len` — средняя длина слова

Эти признаки помогают отличить, например, короткий конфигурационный файл от объёмного текстового документа.

### Векторный подход (TF-IDF) — основное нововведение
Сырой текст передаётся в `TfidfVectorizer` внутри `ColumnTransformer`:

```python
ColumnTransformer([
    ("num",        StandardScaler(),  numerical_cols),    # 50+ числовых
    ("name_tfidf", TfidfVectorizer(analyzer="char_wb", ngram_range=(2,5), max_features=100), "filename_raw"),
    ("content_tfidf", TfidfVectorizer(max_features=500, stop_words="english"), "content_raw"),
])
```

- **Для имени файла:** `char_wb` — символьные N-граммы внутри слов (2-5 символов). Улавливает морфемы: "report", "photo", "main" даже в длинных составных именах.
- **Для содержимого:** word-level — каждое слово становится признаком. `stop_words="english"` убирает неинформативные слова ("the", "and", "is").

**Почему TF-IDF, а не просто подсчёт слов?** TF-IDF автоматически взвешивает слова: частые во всём корпусе (стоп-слова) получают низкий вес, редкие и характерные для конкретного класса — высокий.

## Вопрос 2: Объясните разницу между Bag-of-Words и TF-IDF. Какой метод оказался эффективнее?

### Bag-of-Words (BoW)
Каждый документ представляется вектором, где элемент — **количество вхождений** слова (или бинарный флаг — есть/нет):

```
BoW(t, d) = count(t, d)
```

**Проблема:** частые слова доминируют. Слово "the" в английском тексте может встречаться 100 раз, но не несёт никакой информации о классе файла.

### TF-IDF
Каждый документ представляется вектором, где элемент — произведение частоты слова в документе на обратную частоту по корпусу:

```
TF(t, d) = count(t, d) / total_words(d)
IDF(t)   = ln((1 + N) / (1 + DF(t))) + 1
TF-IDF(t, d) = TF(t, d) × IDF(t)
```

- **TF** — насколько часто слово в данном документе
- **IDF** — насколько слово редкое во всём корпусе. Если слово есть во всех документах, IDF ≈ 0. Если только в нескольких — IDF высокий.

**Ключевое отличие:** BoW считает абсолютную частоту, TF-IDF — взвешенную. Слово "def" в файле с кодом встретится 1-2 раза (высокий TF), но в корпусе файлов оно редкое (высокий IDF) → TF-IDF высокий. Слово "data" может быть частым во всех файлах → IDF низкий → TF-IDF низкий.

### Что эффективнее в проекте?

Мы используем только TF-IDF (не BoW), потому что:
1. **IDF автоматически подавляет шум.** В файлах-документах много общих слов ("report", "company", "year"), которые не помогают классификации. IDF уменьшает их вес.
2. **На имени файла — char_wb.** Символьные N-граммы с TF-IDF дают хорошие признаки даже для коротких имён, где целых слов может быть 1-2.
3. **Меньше фиктивных признаков.** BoW создаёт много признаков для редких слов, которые только шумят. TF-IDF с `min_df=2` и `max_features` отсекает их.

Если сравнивать гипотетически на наших данных: BoW дал бы больше признаков (~1000+ уникальных слов), но много шумовых. TF-IDF (500 признаков для контента + 100 для имени) — компактнее и информативнее.

## Вопрос 3: Как работает наивный байесовский классификатор? Почему он часто используется для текста?

### Математика

Наивный Байес основан на **теореме Байеса**:

```
P(y | x) = P(y) × P(x | y) / P(x)
```

Где:
- **P(y)** — априорная вероятность класса (насколько часто встречается класс в данных)
- **P(x | y)** — правдоподобие (вероятность встретить такой набор признаков x в объекте класса y)
- **P(y | x)** — апостериорная вероятность (искомая — вероятность класса y при данном x)

**«Наивность»** в том, что признаки считаются **условно независимыми** друг от друга при данном классе:

```
P(x | y) = P(x₁ | y) × P(x₂ | y) × ... × P(xₙ | y)
```

Это сильное допущение (в реальности признаки коррелируют), но оно резко упрощает вычисления.

### Для текста — Multinomial Naive Bayes

Вариант НБ, где `P(xᵢ | y)` оценивается как доля слова i в документах класса y (с сглаживанием Лапласа):

```
P(word_i | y) = (count(word_i, y) + α) / (total_words(y) + α × V)
```

Где V — размер словаря, α — сглаживание.

### Почему НБ хорош для текста?

1. **Работает с разреженными данными.** Текстовые признаки — это тысячные векторы с mostly нулями. НБ с этим справляется.
2. **Независимость признаков — не страшна.** Для текста даже при нарушении независимости НБ часто даёт хороший результат (это эмпирический факт).
3. **Быстрое обучение и инференс.** Считается за один проход по данным.
4. **Интерпретируемость.** Можно посмотреть, какие слова сильнее всего влияют на каждый класс.

### Почему в проекте не НБ?

Мы используем LogisticRegression, RandomForest и GradientBoosting — они дают более высокое качество на смешанных данных (числовые признаки + TF-IDF), где НБ хуже работает с числовыми признаками разного масштаба.

## Вопрос 4: Какие метрики вы использовали для оценки качества классификации файлов?

Мы используем **пять метрик**, собранных в `train.py:evaluate_model()`:

### Confusion Matrix (матрица ошибок)
```
          pred: doc  img  arch  code  media  other
true: doc      [167   0     0     0     0      0 ]
      img      [  0  167    0     0     0      0 ]
      arch     [  0    0   167    0     0      0 ]
      code     [  0    0     0   166    0      0 ]
      media    [  0    0     0     0   167     0 ]
      other    [  0    0     0     0     0    166 ]
```
На диагонали — правильные ответы. Вне диагонали — ошибки.

### Precision (точность)
```
P = TP / (TP + FP)
```
Из всех файлов, которые модель назвала "documents", сколько действительно документы? Наказывает за ложные срабатывания.

### Recall (полнота)
```
R = TP / (TP + FN)
```
Из всех настоящих документов, сколько модель нашла? Наказывает за пропуски.

### F1-score
```
F1 = 2 · P · R / (P + R)
```
Гармоническое среднее precision и recall. Единое число, удобное для сравнения.

Используем два варианта усреднения:
- **Macro-F1:** среднее F1 по каждому классу (все классы равны). **Главная метрика.**
- **Weighted-F1:** среднее F1, взвешенное по числу объектов класса.

### Accuracy
```
Accuracy = (TP + TN) / (TP + TN + FP + FN)
```
Простая доля правильных ответов, но может врать при дисбалансе классов.

### Зачем всё вместе?
Accuracy — быстрое понимание. Precision + Recall — детали по каждому классу. F1-macro — объективное сравнение моделей. Confusion matrix — визуальный анализ ошибок.

Выбор лучшей модели — по **F1-macro на test** (строка `train.py:106`):
```python
best_model = max(results, key=lambda k: results[k]["test"]["f1_macro"])
```

## Вопрос 5: Как вы объединили текстовые, числовые и содержательные признаки в одну модель?

### Центральный механизм — `ColumnTransformer` (`model.py:15-25`)

```python
def _build_column_transformer(with_scaler: bool = True) -> ColumnTransformer:
    num_cols = get_feature_columns()  # 50+ числовых признаков
    scaler = StandardScaler() if with_scaler else "passthrough"

    return ColumnTransformer([
        ("num",         scaler,               num_cols),          # (1) числовые
        ("name_tfidf",  TfidfVectorizer(...), "filename_raw"),    # (2) TF-IDF на имя
        ("content_tfidf", TfidfVectorizer(...), "content_raw"),   # (3) TF-IDF на содержимое
    ])
```

**Как это работает:**

```
Входной DataFrame (один файл / строка)
  │
  ├── "filename_len"=22, "kw_images"=1.0, "size_bytes"=1_500_000,
  │   "ext_cat_code"=0.0, "binary_entropy"=6.5, ...  (50+ колонок)
  │   └──→ "num": StandardScaler → [0.2, -1.5, 0.8, ...]
  │
  ├── "filename_raw" = "report_2024"
  │   └──→ "name_tfidf": TfidfVectorizer(analyzer="char_wb", ngram_range=(2,5))
  │         → [0, 0.12, 0, 0.45, 0, 0, ...]  (100 признаков)
  │
  └── "content_raw" = "The company report shows ..."
      └──→ "content_tfidf": TfidfVectorizer(max_features=500, stop_words="english")
            → [0.05, 0, 0.33, 0, 0.12, ...]  (500 признаков)
  
  ↓
  Конкатенация: [0.2, -1.5, ..., 0, 0.12, ..., 0.05, 0, 0.33, ...]
  Единый вектор из 650+ признаков → классификатор
```

### Почему именно так, а не склеить всё вручную?

1. **Без data leakage.** TF-IDF учится на train — `fit_transform()`, на val/test только `transform()`. Если бы мы посчитали TF-IDF на всём датасете до split, модель "подглядела" бы IDF веса из test.

2. **Каждая трансформация своя.** Числовые признаки нужно масштабировать (StandardScaler), текстовые — векторизовать (TF-IDF). `ColumnTransformer` применяет каждый трансформер к своим колонкам.

3. **Pipeline сохраняется.** Когда мы делаем `joblib.dump(model)`, сохраняется весь пайплайн с обученными TfidfVectorizer и StandardScaler. На инференсе просто загружаем `.pkl` и вызываем `predict()` — всё воспроизводится автоматически.

### Откуда берутся сырые тексты?

В `features.py:extract_all_features()` мы добавляем два специальных поля:
- `filename_raw = name_stem.lower()` — стем имени файла (без расширения)
- `content_raw = text` — содержимое текстовых файлов (до 100КБ), или `""` для бинарных

Они сохраняются в CSV вместе с числовыми признаками и загружаются `load_dataset()`.

## Вопрос 6 (доп.): Почему TF-IDF на имя файла использует char_wb с ngram_range=(2,5)?

### Проблема
Имя файла — короткая строка (1-5 слов). Обычный word-level TF-IDF даст 1-5 признаков, что слишком мало. А если имя содержит числа или составные слова ("report_2024", "IMG_1234") — word-level разобьёт их непредсказуемо.

### Решение — символьные N-граммы (char_wb)
`analyzer="char_wb"` выделяет подстроки символов фиксированной длины **внутри границ слов** (пробелы, подчёркивания, точки не пересекает).

**Пример:** имя `"invoice_2024"` с ngram_range=(2,3):
- 2-граммы: "in", "nv", "vo", "oi", "ic", "ce", "20", "02", "24"
- 3-граммы: "inv", "nvo", "voi", "oic", "ice", "202", "024"

`char_wb` в отличие от `char` не создаёт N-граммы, пересекающие границы слов: не будет "e_" или "_2" — только внутри "invoice" и "2024".

### Почему ngram_range=(2,5)?
- **2-3 символа:** ловит короткие корни: "re", "po", "ma", "ph"  
- **4-5 символов:** ловит целые морфемы: "repo", "phot", "scre", "backu"
- **Больше 5:** редко встречается в коротких именах, только шум
- `max_features=100`: оставляем топ-100 самых информативных N-грамм

**Результат:** имя "screenshot_2024.png" превращается в десятки признаков (характерные N-граммы "scre", "hots", "shot"), которые помогают модели отнести его к `images`.

## Вопрос 7 (доп.): Как синтетические данные помогают в обучении?

### Зачем синтетика?
Реальные файлы сложно собрать в нужном количестве с размеченными категориями. Синтетический датасет позволяет:
1. **Контролировать баланс классов** — поровну каждого класса
2. **Получить большой объём** — 5000 файлов за минуту
3. **Проверить пайплайн** — если модель не сходится на синтетике, на реальных данных тоже не сработает

### Как генерируется синтетика (`dataset.py:73-110`)

```
Для каждого класса:
  → выбрать шаблон имени: "invoice_{date}", "main", "IMG_{n}", ...
  → выбрать расширение: .pdf, .py, .jpg, ...
  → выбрать размер: случайно из диапазона класса
  → сгенерировать содержимое:
      - текст (для txt, py, md): корпусные слова по классам
      - бинарное (для jpg, zip, mp3): случайные байты с сигнатурой
  → создать файл на диске
  → extract_all_features() → 50+ числовых + 2 текстовых
```

### Важно: файлы создаются реально на диске
Мы не просто эмулируем признаки — мы создаём настоящие файлы с содержимым, и только потом вызываем `extract_all_features()`. Это гарантирует, что признаки на синтетике будут вести себя так же, как на реальных данных.

## Вопрос 8 (доп.): Что такое data leakage и как вы с ним боретесь?

### Определение
Data leakage — ситуация, когда информация из test-выборки "просачивается" в модель во время обучения. Модель кажется точной на test, но на новых данных падает.

### Источники data leakage в проекте

**1. TF-IDF до разделения (было бы так, но мы так не делаем)**
Если посчитать TF-IDF на всём датасете, а потом разделить на train/test:
- IDF веса будут вычислены с учётом test-документов
- На test модель увидит слова, которых нет в train, но IDF для них уже посчитан
- **Наше решение:** `TfidfVectorizer` внутри `ColumnTransformer` → `fit_transform()` на train, `transform()` на val/test

**2. StandardScaler до разделения**
Если нормализовать все данные перед split:
- Среднее и std посчитаны с учётом test
- **Наше решение:** `StandardScaler` тоже внутри `ColumnTransformer`

**3. Стратификация**
Не даёт утечки, но защищает от другой проблемы: если редкий класс целиком ушёл в test, модель не училась на нём. `stratify=y` гарантирует пропорции классов во всех выборках.

## Вопрос 9 (доп.): Как работает ColumnTransformer под капотом?

### fit() на train

```python
ColumnTransformer.fit(X_train, y_train)
```

1. Для каждой ветки (`"num"`, `"name_tfidf"`, `"content_tfidf"`) извлекаются соответствующие колонки из X_train
2. На каждой ветке вызывается `fit_transform()`:
   - `"num"`: StandardScaler → запоминает μ и σ, нормализует
   - `"name_tfidf"`: TfidfVectorizer → строит словарь N-грамм, считает IDF, возвращает матрицу
   - `"content_tfidf"`: TfidfVectorizer → строит словарь слов, считает IDF, возвращает матрицу
3. Три матрицы конкатенируются по горизонтали (`np.hstack`) → единая матрица признаков

### transform() на val/test

```python
ColumnTransformer.transform(X_val)
```

1. Те же колонки извлекаются
2. На каждой ветке — только `transform()` (без `fit`):
   - Стандартизация с теми же μ и σ
   - TF-IDF с тем же словарём и теми же IDF весами
3. Конкатенация

### На инференсе
Загружается `.pkl` → вызывается `ColumnTransformer.transform()` на одном файле → классификатор предсказывает.

## Вопрос 10 (доп.): Почему все три модели дали F1=1.0?

Это ожидаемо для синтетических данных по нескольким причинам:

1. **Синтетика идеально разделима.** Расширение файла жёстко привязано к классу (например, `.py` всегда код). TF-IDF на имени тоже почти детерминирован: файл с шаблоном "main" всегда код, "invoice_..." — документ.

2. **Классы сбалансированы.** Одинаковое число файлов в каждом классе — никакого дисбаланса.

3. **Шума нет.** Содержимое файла строго соответствует классу (в коде — "def import class", в документах — "company report budget").

На реальных данных будет сложнее: файлы могут быть переименованы, расширения могут не совпадать с классом, содержимое может быть смешанным. Тогда F1 будет ниже и модели начнут различаться по качеству.

## Вопрос 11 (доп.): Что будете делать, если на реальных данных F1 упадёт?

### План действий:

1. **Feature importance анализ.** Random Forest покажет, какие из 650+ признаков реально важны. Возможно, TF-IDF на содержимом шумит, а `ext_group` и `kw_*` — главные.

2. **Настройка гиперпараметров.** Grid Search по `C` для LR, `n_estimators` и `max_depth` для RF/GB, `max_features` для TF-IDF.

3. **Увеличение данных.** Ещё синтетики + сбор реальных файлов.

4. **TF-IDF: подбор параметров.** Увеличить/уменьшить `max_features`, попробовать другие `ngram_range`, добавить `max_df` для отсева слишком частых слов.

5. **Новые признаки.** Добавить TF-IDF на темы (через LDA), или байтовый Transformer для бинарных файлов (из раздела "Развитие" в README).
